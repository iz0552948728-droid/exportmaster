# Язык шаблонов

Описание формата шаблона и правил формирования выходного файла.
Составлено по ТЗ ред. 1.0 от 29.07.2026 с учётом решений, согласованных в переписке.

---

## Что делает модуль форматирования

Шаблон — это **форма будущего выходного файла** (csv или txt), а не документ для отображения.
Расширение `.md` — соглашение; как разметка markdown шаблон не разбирается.

Тело шаблона копируется в результат **байт в байт**; заменяются только специальные поля.
Отсюда следствие: структура csv (разделители, порядок колонок, шапка таблицы) живёт
в шаблоне, а не в коде модуля.

---

## Структура файла шаблона

```
[MDHEADER]
… специальные поля заголовка …
[/MDHEADER]
… тело: текст будущего файла со специальными полями …
```

### Правила разбора заголовка

1. `[MDHEADER]` и `[/MDHEADER]` занимают строку целиком; окружающие пробелы и табуляции
   игнорируются, ничего другого в строке быть не должно.
2. Распознавание без учёта регистра; канон — прописными.
3. `[MDHEADER]` должен быть первой непустой строкой файла. BOM и пустые строки перед ним
   отбрасываются.
4. Открывающий тег без закрывающего — ошибка разбора. Молчаливый откат к «файлу без
   заголовка» недопустим: служебные строки уехали бы в результат незамеченными.
5. Тело начинается с символа, следующего за переводом строки после `[/MDHEADER]`;
   сам этот перевод строки в выходной файл не попадает.
6. В теле `[MDHEADER]` и `[/MDHEADER]` — обычный текст, попадает в результат как есть.
7. Внутри заголовка допустимы только специальные поля и пустые строки; произвольный
   текст — ошибка, так ловятся опечатки в именах полей.

Заголовок обязателен: без него неоткуда взять имя выходного файла.

---

## Специальные поля

Заголовок и тело используют один и тот же синтаксис. Поле — набор кодовых слов
в фигурных скобках. Литеральные скобки записываются как `{{` и `}}`.

Внутри списка аргументов записи `X(...)` и `{X(...)}` равнозначны: фигурные скобки
обязательны только на верхнем уровне тела. Это согласует таблицу синтаксиса п. 4.4.3.3
ТЗ с приведённым там же примером `AMP({VALUE(...)})`.

Кавычка внутри строкового литерала экранируется удвоением: `""`.

> Полный состав полей и встроенных функций — предмет отдельного согласования
> (третий этап). Ниже зафиксировано только то, что уже решено.

### Поля заголовка

| Поле | Назначение |
|---|---|
| `{FILENAME(...)}` | способ формирования имени выходного файла, вместе с расширением |
| `{GROUPBY(...)}` | список осей, по которым идёт итерирование (аналог `GROUP BY`) |
| `{ENCODING(...)}` | кодировка выходного файла |
| `{DECIMAL(...)}` | десятичный разделитель |
| `{NEWLINE(...)}` | переводы строк |

Имена осей в `{GROUPBY(...)}` — значения перечисления `Dimensions`
(`FREQ`, `POL1`, `CHANNEL`, `BEAM`, `DATA`, `POS`, `SLIDER`, `POL2`),
см. `format-spec.md`. Пишутся строками: `{GROUPBY("POL1", "SLIDER", "CHANNEL", "BEAM")}`.

### Отбор данных и текущее значение оси

`{GROUPBY(...)}` разбивает многомерную матрицу на **двумерные** вырезки: сначала по первой
оси списка, внутри неё по второй и так далее. На каждую комбинацию значений формируется
свой выходной файл.

Отсюда основное правило: **число осей в `{GROUPBY(...)}` равно размерности матрицы
минус два.** Две оси, не попавшие в список, остаются в вырезке и становятся строками
и колонками табличной подстановки. Для шестимерной матрицы это четыре оси разбиения:

```
{GROUPBY("POL1", "SLIDER", "CHANNEL", "BEAM")}
{TABLE("FREQ", "DATA", "AMP", "0.00", ";")}
```

Из правила следуют две проверки, выполнимые до чтения данных: ось таблицы не может быть
осью разбиения, а строки и колонки должны идти по разным осям. Само равенство числа осей
проверяется по описателю измерений из файла данных — вместе с его чтением.

Ось с одним-единственным значением ведёт себя как любая другая: разбиение по ней даёт
одну группу. Лучей, каналов или положений слайдера может быть по одному — на устройство
шаблона это не влияет.

`{GROUPVALUE("<ось>")}` подставляет текущее значение оси разбиения — то, которое
соответствует формируемому в этот момент файлу. Обычно используется в имени файла,
чтобы файлы разных групп не перезаписывали друг друга. Ось должна быть перечислена
в `{GROUPBY(...)}`: у оси, оставшейся внутри вырезки, текущего значения нет.

### Табличная подстановка

```
{TABLE(<заголовки колонок>, <заголовки строк>, <функция данных>, <формат>, <разделитель>)}
```

Единственное поле, порождающее не одно значение, а сетку. Работает над двумерной
вырезкой, оставшейся после разбиения по `{GROUPBY(...)}`. Правила:

- **заголовки строк и колонок печатает сама таблица**, беря значения из метаданных осей.
  Вписать их в шаблон руками нельзя: значения приходят из данных и заранее неизвестны;
- **разделитель ячеек** задаётся пятым аргументом и обязателен: у разных таблиц одного
  файла он может различаться, поэтому в заголовок шаблона его не выносят. Молчаливое
  умолчание здесь опаснее ошибки — файл получился бы правдоподобным, но с чужим
  разделителем;
- **угловая ячейка** на пересечении заголовков пуста;
- **последняя строка таблицы** переводом строки не завершается — его ставит шаблон.

## Выходной файл

| Свойство | Умолчание | Переключается |
|---|---|---|
| Кодировка | UTF-8 без BOM | `{ENCODING("UTF-8-BOM")}`, `{ENCODING("CP1251")}` |
| Десятичный разделитель | точка | `{DECIMAL(",")}` |
| Переводы строк | как принято в операционной системе | `{NEWLINE("CRLF")}`, `{NEWLINE("LF")}` |
| Имя файла | из `{FILENAME(...)}`, вместе с расширением | — |

Во входном шаблоне BOM игнорируется при чтении: Блокнот и Visual Studio ставят его
самостоятельно, и без этого правила заголовок молча не распознавался бы.

**Кого читает выходной файл, решает автор шаблона.** Умолчание — UTF-8 без BOM: его ждёт
программа заказчика, и три лишних байта в начале первого поля ей мешают. Но Excel при
двойном клике по csv кодировку не спрашивает и берёт системную однобайтную, поэтому
UTF-8 без BOM он покажет как мусор. Шаблон, предназначенный для просмотра человеком,
должен явно требовать `{ENCODING("UTF-8-BOM")}` либо `{ENCODING("CP1251")}`.
Образец `samples/templates/example.md` просят открывать глазами, поэтому в нём стоит BOM.

Десятичный разделитель намеренно не берётся из локали системы: одно и то же задание
на двух машинах давало бы разные файлы, а разбирающая сторона у заказчика ждёт что-то одно.

## Запуск модуля

### Параметры командной строки

| Ключ | Назначение |
|---|---|
| `/source <алиас>:<файл>` | файл данных под заданным алиасом; можно указывать многократно |
| `/md <файл>` | файл шаблона |
| `/target <путь>` | каталог для результата |
| `/id <идентификатор>` | идентификатор задания |
| `/key <ключ>` | сформировать файл для конкретного значения ключа |
| `/overwrite yes\|no` | перезаписывать существующий файл; по умолчанию `yes` |
| `/stub descriptive\|sample` | вид заглушек вместо значений; ключ отладочный, вне ТЗ |

Каждый ключ дополнительно принимается в длинной форме (`--source` и так далее):
п. 4.9 ТЗ допускает Linux, где `/source` неотличим от абсолютного пути.

Программа командной строки не взаимодействует с пользователем в процессе исполнения
(п. 4.1.5 ТЗ). Поэтому вопрос о перезаписи задаётся ключом, а не диалогом; спрашивать
будет только диалоговый режим.

### Стандартный вывод

По строке на каждый сформированный файл, пять полей через табуляцию:

| № | Поле |
|---|---|
| 1 | идентификатор задания из `/id` |
| 2 | код результата: `0` — ОК, `1` — не ОК |
| 3 | ключ результирующего файла, например `POL1=1;FREQ=1.2e9;CHANNEL=2` |
| 4 | имя результирующего файла |
| 5 | текст сообщения об ошибке, если код `1` |

**Стандартный вывод принадлежит только этому протоколу.** Диагностика идёт в логи и
в stderr: его разбирает программа заказчика, и одно отладочное сообщение сломает разбор.

### Коды возврата процесса

| Код | Значение |
|---|---|
| `0` | все файлы сформированы |
| `1` | сформированы частично |
| `2` | задание не выполнено: ошибка в аргументах, шаблон не разобран |

### Ошибки в задании

Не найден алиас, нет поля в векторе, индекс вне диапазона — выходной файл **не создаётся**,
в вывод идёт строка с кодом `1` и текстом ошибки. Файл с молчаливо пропущенным значением
опаснее отсутствующего: он выглядит рабочим.

### Логи

Пишутся в папку `LOGS` рядом с исполняемым файлом, хранятся за последние 10 дней (п. 4.1.4 ТЗ).
Отдельный конфигурационный файл пока не заводится: всё, что нужно модулю форматирования,
задаётся в заголовке шаблона.

## Отличия от ред. 1.0 ТЗ

| Что | В ред. 1.0 | Согласовано |
|---|---|---|
| Разделитель заголовка шаблона | «служебные символы», без конкретики | `[MDHEADER]` / `[/MDHEADER]` |
| Имя поля отбора данных | не задано | `{GROUPBY(...)}` |
| Текущее значение оси разбиения | отсутствует | `{GROUPVALUE("<ось>")}` |
| Представление таблицы | не задано | заголовки из метаданных, разделитель — пятый аргумент, угловая ячейка пуста |
| Экранирование кавычки | не задано | удвоение `""` |
| Коды возврата процесса | не описаны | `0` / `1` / `2` |
| Ключ `/overwrite` | отсутствует | добавлен |
| Имя первой поляризации в примере п. 4.4.5 | `P1` | `POL1` |

Ключ `/key` на первом этапе принимается и проверяется, но отбор по нему не выполняется.

## Заглушки вместо значений

Пока файлы данных не читаются, специальные поля заменяются заглушками. Это позволяет
прогнать шаблон и увидеть форму будущего файла до появления измерений, а заодно
проверить сам шаблон на ошибки.

| Режим | Что подставляется |
|---|---|
| `descriptive` (по умолчанию) | описание поля в угловых кавычках: `‹FIELD("MEAS", "POW")›` |
| `sample` | правдоподобное число, отформатированное строкой формата из шаблона |

Режим `sample` даёт файл, который открывается в Excel, — структура видна как есть.
Числа выводятся устойчиво: одинаковые поля дают одинаковые значения при любом запуске,
иначе эталонные файлы было бы не с чем сравнивать.

Табличная подстановка в обоих режимах разворачивается в сетку 3 × 4 со своими
заголовками строк и колонок: реальные размеры придут из метаданных осей.

В имени файла заглушки собираются в короткой форме: `{FIELD("MEAS", "NAME")}` даёт
`MEAS.NAME`, `{GROUPVALUE("POL1")}` — `POL1`. Полная запись поля со скобками и кавычками
дала бы нечитаемое имя, а кавычки в именах файлов Windows не допускает вовсе.
