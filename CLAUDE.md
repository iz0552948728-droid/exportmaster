# ExportMaster

МАСТЕР ЭКСПОРТА РЕЗУЛЬТАТОВ ИЗМЕРЕНИЙ — модуль форматирования.
Извлекает результаты из файлов измерений, сливает их с markdown-шаблоном и сохраняет
в формате заказчика. Работает в режиме командной строки и (позже) в диалоговом режиме.

## Сборка и проверка

```bash
dotnet build
dotnet test
```

Требуется .NET 8 SDK. В сессиях Claude Code он не предустановлен:
`apt-get install -y dotnet-sdk-8.0` (пакет есть в архиве Ubuntu; `dot.net` и
`builds.dotnet.microsoft.com` заблокированы политикой сети).

## Раскладка

| Проект | Назначение |
|---|---|
| `src/ExportMaster.Template` | лексер, парсер шаблона в дерево, валидатор |
| `src/ExportMaster.Engine` | вычисление полей, рендер, формирование выходных файлов |
| `src/ExportMaster.Formatter.Cli` | разбор командной строки, протокол вывода, логи |
| `src/ExportMaster.Gui` | диалоговый режим (появится позже, `net8.0-windows`) |

Зависимости строго вниз: `Cli` → `Engine` → `Template`/`Formats` → `Core`.

## Правила, которые нельзя нарушать

**Ядро кроссплатформенно.** Всё, кроме `Gui`, таргетит `net8.0`. Windows-only API в
`Template`, `Engine` и `Cli` закрывают п. 4.9 ТЗ (возможен Linux) и лишают возможности
собирать и тестировать проект в этой сессии.

**Стандартный вывод принадлежит протоколу п. 4.3.3 ТЗ.** Никаких `Console.WriteLine`
по коду — только через единственный `ResultWriter`. Диагностика идёт в stderr и в логи.
Вывод разбирает программа заказчика, одно отладочное сообщение ломает разбор.

**`IValueResolver` — главный шов.** Первый этап подставляет заглушки
(`StubValueResolver`), третий — реальные данные (`BinaryDataResolver`). Парсер, рендерер,
командная строка и формат вывода при этом не меняются.

**`GROUPBY` оставляет ровно два измерения.** Число осей разбиения равно размерности
матрицы минус два; оставшиеся две оси и есть строки и колонки `TABLE`. Размерность
не фиксирована — она задаётся описателями измерений конкретного файла данных, поэтому
шаблон привязан к форме данных, под которую написан. Проверки, не требующие данных,
живут в `SemanticValidator`; равенство числа осей и наличие каждой названной оси
проверятся по описателям, когда появится чтение bin.

**Значения осей превращает в текст `AxisValueFormatter`, а не описатель.** Как показать
частоту, решает шаблон: единица выбирается по величине (гигагерцы от 1 ГГц, ниже —
мегагерцы), число знаков задаёт директива `AXISFORMAT`. Описатель оси знает только
хранимое значение.

**Ошибки — диагностика, а не исключения наружу.** Неудачный срез даёт строку с кодом `1`,
а не падение всего задания (п. 4.7 ТЗ: отказы не допускаются).

**Идентификаторы кода — по-английски.** Имена типов, методов, полей, параметров и
тестов пишутся латиницей, включая названия тестовых методов. По-русски пишутся только
комментарии, XML-документация, сообщения об ошибках и документы в `docs/`.

**Перечисление `Dimensions` имеет явные значения 1…8.** Нумерация с нуля прочитает не ту
ось и выдаст правдоподобные, но неверные числа — без падения.

## Договорённости по формату

Всё согласованное зафиксировано в:

- `docs/format-spec.md` — двоичные форматы файлов данных;
- `docs/template-language.md` — язык шаблонов, командная строка, протокол вывода.

Оба документа перечисляют отличия от ТЗ ред. 1.0, которые нужно внести в новую редакцию.
При расхождении кода с этими документами прав документ — либо, если решение изменилось,
сначала правится документ.

## Этапы

| Этап | Содержание | Состояние |
|---|---|---|
| 0 | Каркас решения, настройки сборки, документы | готов |
| 1 | Лексер и парсер шаблона | готов |
| 2 | Валидатор шаблона | отложен: нет состава полей |
| 3 | Рендер с заглушками, командная строка, логи | готов |
| 4 | Чтение файлов данных (`.mtx`) | готов |
| 5 | Подстановка реальных значений, `GROUPBY`, таблицы | готов |
| 5а | Чтение файлов вектора (сигнатура 2) | ждёт образца |

Порядок этапов 2 и 3 переставлен: валидатор требует состава полей и функций,
а он ещё не согласован. Рендер с заглушками от него не зависит.
| 6 | Диалоговый режим | — |

Раскладка `.mtx` подтверждена на образце `samples/data/aaa.mtx`; отличия от ТЗ ред. 1.0
перечислены в `docs/format-spec.md` и подлежат внесению в новую редакцию.

Порядок следования данных образцом **не подтверждён**: файл заполнен числами без
внутренней структуры. Нужен файл, где значение выводится из индексов точки, — только
так ошибка в раскладке осей ловится до приёмки.

`{FIELD(...)}` пока даёт предупреждение и заглушку: формат вектора образцом не подтверждён.

Смысл функции `AMP` принят как `20·log10(|z|)` — по примеру ТЗ п. 4.4.3.3, где её
результат подписан «дБ». Линейный модуль доступен отдельно как `MAG`. Перечень величин
будет задан перечислением на стороне заказчика разработки.

## Тесты

Проверки лексера и парсера пишутся сразу — в том числе на двух примерах специальных полей
из п. 4.4.3.3 ТЗ, которые обязаны разбираться дословно.

Приёмочные тесты (шаблон на входе, эталонный файл на выходе) ждут реального шаблона
от автора ТЗ. Эталоны лежат в `samples/`, сравниваются побайтно; `.gitattributes`
запрещает git трогать в них переводы строк.

## Работа с репозиторием

Основной репозиторий проекта — GitLab заказчика во внутренней сети, недоступный извне.
Этот GitHub-репозиторий — рабочая площадка на время разработки; изменения переносятся
в GitLab выгрузкой на стороне заказчика.

Коммиты идут в `main`, по одному на законченный шаг. История не переписывается:
ни `push --force`, ни `amend` над отправленными коммитами — любое прошлое состояние
должно оставаться достижимым.
